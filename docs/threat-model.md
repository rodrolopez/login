# Modelo de amenazas — Identity API

**Revisión:** Fase 10, 2026-10-26  
**Alcance:** API Express, autenticación local y federada, OIDC, sesiones, recuperación, autorización multi-tenant y dependencias actuales.

## Activos y límites de confianza

- Credenciales de usuario, correos, tokens de acción, sesiones API y artefactos OIDC.
- Datos y roles de cada organización, además de eventos de auditoría.
- Secretos de PostgreSQL, Redis, Google OAuth y claves OIDC almacenados fuera del código.
- El cliente HTTP y sus encabezados/payloads son no confiables. La autorización tenant se consulta en PostgreSQL; los identificadores enviados por el cliente no otorgan permisos.
- PostgreSQL y Redis de pruebas están aislados de los servicios de desarrollo y producción.

## Política HTTP y CORS

- La API no refleja orígenes arbitrarios ni acepta `*` con credenciales. `CORS_ALLOWED_ORIGINS` contiene orígenes exactos separados por comas, sin rutas ni comodines; en producción solo admite HTTPS. El mismo origen se reconoce por esquema y `Host` de la solicitud. Sin lista configurada, no se habilitan orígenes adicionales.
- La API permite `GET`, `POST` y `PATCH`, y los encabezados `Accept-Language`, `Authorization` y `Content-Type`; rechaza métodos/cabeceras de preflight fuera de esa lista.
- Los endpoints públicos de discovery y JWKS de OIDC no requieren credenciales y pueden conservar CORS de lectura pública del proveedor. Los endpoints CORS asociados al cliente usan los redirect origins registrados y no admiten el origen `null`.
- HSTS se activa con `NODE_ENV=production`; el entorno de despliegue debe terminar TLS correctamente. El proxy inverso y su política de hosts confiables se revisarán en la preparación de producción.

## Riesgos residuales

- CORS y `Origin` no sustituyen autenticación ni autorización. Clientes no navegador pueden falsificar encabezados; los controles de identidad, permisos y estado de sesión siguen siendo la barrera principal.
- Discovery y JWKS son datos públicos por diseño y no llevan `Access-Control-Allow-Credentials`. El acceso de lectura cruzado a esos documentos no expone secretos.
- Los límites Redis protegen la aplicación, pero no reemplazan WAF/CDN ni mitigación volumétrica antes de Node.js. Esa capa sigue pendiente de la Fase 13.
- `trust proxy` está desactivado. Si se despliega detrás de un proxy y no se configura una cadena de proxies confiables, el rate limit agrupará tráfico detrás de la IP del proxy; habilitar confianza indiscriminada permitiría falsificar IPs.
- HSTS depende de que el despliegue use HTTPS y de que `NODE_ENV` sea `production`. No se debe activar producción detrás de un endpoint público HTTP.
- CSP está configurado para respuestas API sin recursos de navegador. Si se agregan pantallas HTML, redirects con contenido o documentación interactiva, la política debe revisarse con esas rutas y probarse en navegador.
- `npm audit` informa avisos conocidos publicados por el registro consultado; no detecta fallos lógicos, dependencias comprometidas no reportadas ni vulnerabilidades desconocidas.
- No se ejecutó escaneo dinámico externo, fuzzing continuo, análisis SAST especializado, ni pruebas de carga. La suite adversarial es una cobertura acotada, no una certificación de seguridad.
